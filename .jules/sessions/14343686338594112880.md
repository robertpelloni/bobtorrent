# BobTorrent Project Memory & Architectural Summary

## 1. Project Overview & Omni-Workspace Concept
**BobTorrent** is a decentralized, anonymity-focused peer-to-peer file sharing and predictive streaming platform. The repository is structured as an **Omni-Workspace**, a centralized command center that orchestrates multiple independent components and submodules.

*   **Legacy Components (Archived/Deprecated):** Node.js Reference Client, Java Supernode, and a C++ qBittorrent submodule.
*   **Current State (v11.60+):** The architecture has fully pivoted to a native, high-performance Go ecosystem consisting of specialized, communicating binaries (`supernode-go`, `lattice-go`, `dht-proxy`) and WASM browser targets. The ecosystem also encompasses the `bobcoin` (economy and gaming layer) submodule.

## 2. Core Architecture & Services (Go Ecosystem)
The Go implementation is divided into highly concurrent, specialized components operating out of `cmd/` and `internal/`:

*   **`supernode-go` (The Main Orchestrator):**
    *   Acts as the central tracker (HTTP and UDP BEP 15) and primary file ingestion/seeding node using `anacrolix/torrent`.
    *   Hosts the comprehensive Web UI (`web/ui`) and terminal dashboard (TUI via `bubbletea`).
    *   Provides high-level APIs for identity (`/key/generate`), ingestion (`/ingest`), publishing (`/publish`), and tracking subscriptions (`/subscribe`, `/subscriptions`).
*   **`lattice-go` (The Consensus Layer):**
    *   Manages an asynchronous, local block-lattice engine that governs economy (Bobcoin), NFTs, and metadata anchoring.
    *   Provides a persistent, snapshot-capable SQLite backend.
    *   Emits real-time block events via WebSockets to keep frontends and other nodes (like the supernode) synchronized.
*   **`dht-proxy` (Privacy Routing):**
    *   Operates a standalone Kademlia DHT node, insulating end-users from direct IP exposure to public DHT networks.
*   **WASM Storage Bridge (`cmd/wasm`):**
    *   Compiles the core storage primitives (ChaCha20-Poly1305 encryption, Reed-Solomon erasure coding) into WebAssembly (`storage.wasm`).
    *   Enables zero-trust, browser-side file sharding and encryption directly in the UI before data hits the supernode.

## 3. Storage & Cryptography Patterns
*   **Erasure Coding & Encryption:** Files are erasure-coded (data+parity shards) and encrypted with AES-256-GCM / ChaCha20-Poly1305.
*   **Content-Addressed Shards:** Encrypted shards are uploaded to the supernode (`/upload-shard`) and durably persisted based on their SHA-256 hashes inside `internal/publish/registry.go`.
*   **Manifest Publication (BEP 44):** The system generates JSON manifests containing the metadata necessary to reconstruct and decrypt the original file. These manifests are signed by Ed25519 identity keys and published via the BitTorrent Mainline DHT using BEP 44 mutable items.

## 4. UI & Pub/Sub Mechanics
*   **Channel Subscriptions:** Users can subscribe to publisher channels by tracking their public Ed25519 keys. The supernode holds active subscriptions in memory (`subscriptionStore`) and polls the DHT to discover new manifests anchored to those keys.
*   **Dashboard Telemetry:** The backend exposes a `/stats` endpoint that merges real-time metrics across storage utilization, active BitTorrent swarms, DHT routing health, Filecoin bridge status, and active Pub/Sub subscription counts. The Web UI continuously polls this to provide a live "Status" dashboard.

## 5. Development & Autopilot Protocols
The Omni-Workspace enforces strict operational rules defined in `UNIVERSAL_LLM_INSTRUCTIONS.md` to ensure autonomous agents can continuously improve the codebase:

*   **Single Source of Truth:** `VERSION` dictates the global release number. Everything else derives from it.

*   **Verifiable Output:** Agents are required to compile the Go binaries (`go build -buildvcs=false ./...`), pass the internal test suite (`go test -v ./...`), and avoid leaving behind temporary scripts or patch files before committing.
*   **Refactor Policy:** Pragmatic, project-aligned improvements are favored over radical pivots. Preserve existing functionality and unify systems rather than rewriting them from scratch unless directed.

*   **Immediate Next Steps:** Finalizing the backend's automatic persistence and fetching logic for new BEP 44 manifests as they arrive over the DHT polling routines, and integrating specific game engine asset ingestion paths for the upcoming Bobcoin ecosystem launch.
